7.3.1 -- 2026-09-19
--------------------
- Fixed three follow-up bugs in the "Create your library" gate (7.2.0-7.2.2 above) found by actually using the merged fix. First, the invite-accept popup lost track of an open invitation on any navigation without a `?invite=` URL param -- e.g. going to the site footer's Privacy link and back, or the header logo -- so it fell back to showing "create your library" instead, even though the person still had a pending invite waiting. `ZeroLibraryContent` used to read `?invite=` off the URL alone; the nested `(library)` route group's layout (see below) now also looks up an open `LibraryInvite` by the signed-in user's email server-side and passes its token down as `pendingInviteToken`, so the invite-accept popup keeps showing on a bare revisit to `/dashboard` with no query string at all, not just the one page load that actually carried the link. `InviteAcceptOverlay` gained an optional `token` prop (falls back to the `?invite=` URL param when omitted, so the existing overlay-variant usage is unchanged) and an `onDismiss` callback, since a server-known token has no URL param for "Not now" to strip.
- Second, the header's logo in the library-less state wasn't a link at all (unlike the same header once a library exists, which already wrapped it in `<Link href="/dashboard">`) and was rendered smaller (26px) than the site footer's (36px) right next to it on the same screen -- both fixed in `src/app/dashboard/layout.tsx`'s zero-membership header branch to match the footer exactly.
- Third, `/dashboard/profile` was unreachable without a library -- the dashboard layout's zero-membership branch unconditionally replaced every child route's content with the create-library/invite-accept gate, even though the Profile page has no library dependency of its own (it only needs the signed-in user). Root-caused to a hard constraint: a shared Next.js layout has no way to know which child route is actually being rendered, so a blanket "always show the gate" check couldn't distinguish Profile from the library-dependent pages. Fixed by moving every library-dependent route (Overview, Library, Scan, People, Shelves, Settings, book/shelf detail) into a new `src/app/dashboard/(library)/` route group with its own nested layout that does the gating, while `/dashboard/profile` stays a plain sibling outside that group and is now always reachable regardless of membership state -- route groups don't change any URL, so every route keeps working exactly where it already was. `getCurrentUser()` (`src/lib/auth.ts`) is now wrapped in React's `cache()` since both the top-level dashboard layout and the new nested gate layout call it on every request for a library-less account; without that it'd be a redundant extra database query per page load.
- Verified with a live local Playwright run (15/15 new checks): an invite-accept popup created via a fresh invite signup survives navigating to the Privacy page and back (no `?invite=` in the URL afterward) and a bare `/dashboard` revisit, rather than falling back to the create-library popup, and still accepts correctly into the shared library; the header logo in the library-less state links to `/dashboard` and matches the footer logo's height exactly; `/dashboard/profile` renders its real form (not the gate) both via direct navigation and via the header's profile dropdown while library-less, while a library-gated route (`/dashboard/search`) still correctly shows the gate in the same account state. Also re-ran the existing 12-check and 24-check popup/invite regression suites (51 checks total) to confirm nothing else regressed. Test data cleaned up from the local database afterward.


7.3.0 -- 2026-09-19
--------------------
- Added a diagnostic log for ISBN lookups, from Jack noticing lots of his real-world scans were failing to find book details and wanting visibility into why. His first idea was a text file, but Stacks runs on Vercel, where each function invocation gets its own ephemeral filesystem that's wiped on every redeploy and isn't shared across concurrent instances -- a log file would constantly lose data. Logs to a new `BookLookupLog` table on Postgres instead (already the app's own datastore), one row per lookup attempt: the ISBN, which library scanned it, what triggered it (`scan-in`, `scan-in-retry` for a later scan of an already-manual-unresolved book, or `manual-button` for the edit page's "Look up this ISBN"), whether each of Google Books and Open Library was actually called, each one's outcome (`success` / `no-match` / `http-error` with the real HTTP status / `network-error` with the real error text, e.g. a timeout), and whether the attempt ultimately resolved a title. `src/lib/books.ts`'s `lookupBookByIsbn` now returns these diagnostics alongside its existing result so the three call sites (scan-in's new-ISBN path, its manual-unresolved retry path, and the edit page's manual lookup route) can each log via the new `src/lib/book-lookup-log.ts` helper; CSV import is untouched since it deliberately never calls either API. Jack asked to skip building an in-app viewer for it -- he already has Neon access and would rather query the table directly than have one maintained in the app.
- Verified with a live local Playwright run (12/12 checks) against the real Google Books and Open Library APIs (not mocked): a real ISBN correctly logged as `scan-in` with Open Library's real response; an ISBN neither catalog has correctly logged as unresolved with both providers' real failure reasons captured (in this sandbox: Google Books' daily quota genuinely exhausted, returning a real `HTTP 429`, and Open Library genuinely returning `HTTP 404` for the made-up ISBN); a second scan of that same still-unresolved ISBN correctly logged as `scan-in-retry` rather than `scan-in`; and clicking "Look up this ISBN" on the edit page correctly logged as `manual-button`. Test data (including the shared placeholder `Book` rows the failed lookups created) cleaned up from the local database afterward.

- Reworked the Settings members table's role editing, from a project-thread request bundling four related changes. "Make owner" moved off its own always-visible button and into each row's role dropdown, now offered only on rows whose current role is Admin -- the server enforces this too (`POST /api/library/transfer-ownership` now 409s if the target isn't already an Admin), not just the UI, matching how the existing Owner-row protections in that file are already enforced. All four role-dropdowns are now a fixed width regardless of whether "Make owner" is in their option list, so a View Only row's select isn't narrower than an Admin's.

6.20.0 -- 2026-09-18
--------------------
- Scanning out an ISBN that matches more than one copy in the library now shows a picker (shelf name, Available/Reserved status, and who a reserved copy is held for) instead of silently guessing -- `POST /api/copies/scan-out` returns `{ choices: [...] }` when the ISBN has multiple non-removed copies, and a follow-up call with `copyId` finalizes the one the user actually picked. Previously it always auto-picked the oldest AVAILABLE copy, falling back to the oldest RESERVED copy only if none were available, with no way to tell the app which physical copy was in hand and no shelf shown in the result -- if two copies of the same title were reserved for different people, or one was reserved and another wasn't, the wrong reservation could get silently released. Came from a project-thread question about how duplicate-ISBN scan-out behaves; flagged the ambiguity, mocked up the picker as an Artifact (https://claude.ai/artifact/RyTHBu8RFL1g57AXcY5G2x), and built it once Jack said to go ahead. A single matching copy still resolves immediately with no extra step, same as before.
- The scan-out result banner now names the shelf the removed copy came from ("Removed from Shelf B2." / "Removed from Shelf B2 -- reservation for X marked fulfilled.") instead of the generic "Removed from your library." -- needed so the new picker's choice is visibly confirmed, and fixes the same shelf-blindness for the everyday single-copy case too.
- Verified with a live local Playwright run against local Postgres: a single-copy ISBN still resolves instantly with no picker; two available copies show a picker listing both shelves, Cancel backs out with no side effects, and picking one removes exactly that copy while the other stays untouched and the next scan of the same ISBN auto-resolves to it; a mixed available/reserved pair shows the reservation warning before removal, removing the available copy leaves the reservation active, and removing the reserved copy (once it's the only one left) correctly releases it (21/21 checks passed).

A migration backfilled the new column for existing copies. Import's Copy-ID matching now looks up by this code instead of the raw ID -- nothing else in the app displayed or depended on the old raw ID, so the change is contained to export, import, and copy creation.


6.4.0 -- 2026-09-17
--------------------
- Added a real permission system: alongside Owner, a library now has Admin, Member, and View Only roles, replacing the old setup where every non-owner had the same access and "Admin" existed in the schema but nothing could ever grant it. Admin can do everything a Member can plus manage shelves, invite links, CSV import, and other members' roles. Member can scan/reserve/edit books but not touch settings. View Only is read-only -- can't scan, reserve, edit, or add notes at all. Rules worked out and agreed with the user before building: Member is deliberately excluded from CSV import (not just shelf management) because import auto-creates a Shelf row for any unrecognized shelf name in the file, which would otherwise let a Member create shelves indirectly through the back door of a feature they're supposed to be locked out of.
- The single library-wide invite link is now three separate links -- "Invite as Admin", "Invite as Member", "Invite as View Only" -- each independently generated/regenerated in Settings, since there's still no transactional email to target an invite at one person's role individually. Owner is never a link target; the only way to become Owner is a transfer. `Library.inviteCode` (unique, single column) is replaced by `inviteCodeAdmin`/`inviteCodeMember`/`inviteCodeViewOnly`; the migration copies any already-shared link into `inviteCodeAdmin` so it keeps granting the same access it always did (the old link always granted full read/write access, which is what Admin represents now).
- Added ownership transfer ("Make owner" on another member's row) -- the only way anyone, including the current Owner, stops being Owner. A Membership row with role OWNER can never be deleted or have its role changed through the regular member-management endpoints (enforced server-side, not just hidden in the UI), so an Owner who wants to leave the library transfers ownership first, then removes their own now-Admin membership like anyone else. This also means an Admin can never remove or demote the Owner, by construction rather than by a member-count check.
- Every plain "Member" from before this change is promoted to Admin in the migration -- that role already had full read/write access (everything short of managing members/invites/deleting the library, none of which the old UI even exposed), so nobody's access shrinks the moment this ships. The new, narrower "Member" tier only applies to accounts created after this point.
- Centralized the role checks in src/lib/permissions.ts and a `require: "edit" | "manage"` option on requireLibraryContext (src/lib/api-context.ts) rather than repeating role comparisons in every route, and a LibraryRoleProvider React context (src/components/library-role-context.tsx) so client components (the Scan station, the Library browse/grid view, book detail) can hide actions a View Only member can't take without each one re-deriving the role from scratch.

6.2.0 -- 2026-09-16
--------------------
- Added a real progress indicator to the import loading screen: a determinate progress bar, a "Row X of Y" counter with percentage, a ticker naming the book currently being processed, and a live New/Updated/Skipped tally that updates as it goes -- so a large import (hundreds of rows) reads as visibly working the whole way through, not just a static "Importing..." label for however long it takes. Mocked up first as an Artifact over a couple of rounds before building.
- This required changing how import actually runs, not just the UI: previously the whole file was sent as one request that only replied once every row was done, which had two problems -- no way to show real progress mid-request, and (worse) a real risk of the whole thing rolling back or dying if the connection dropped before that one giant response ever came back. Now the client splits the file into batches of 10 rows and sends them one at a time, each one committing fully before the next is sent, so closing the tab mid-import only loses whatever hasn't been sent yet -- everything already processed stays saved. If a batch request fails outright, the confirm screen reports exactly how many of the file's rows made it in before stopping, since by then some already have -- re-running the same file is safe and picks up the rest (Copy-ID-matched rows just re-match harmlessly).
- The progress bar/ticker still read as continuously moving even though the batches arrive in chunks: each batch's rows are revealed to the UI one at a time at a pace that adapts to how long that batch actually took, rather than jumping straight to the new totals the instant a batch's response lands. The import endpoint now returns a per-row outcome list (not just aggregate counts) specifically so the client has real data to animate through, rather than faking movement.

6.0.0 -- 2026-09-15
--------------------
- Added CSV backup and import to Settings, in a new "Backup & Import" block. Mocked up first as an interactive Artifact over several rounds before any code was written -- see that session's design decisions below, since most of this feature's behavior was worked out there rather than while building.
- Backup: a "Download CSV backup" button exports every non-removed copy (Copy ID, ISBN, effective title/authors/publisher, shelf, status, reservation, notes, BookCrossing ID, date added) using the library's override-merged view (applyBookOverride), so a backup reflects what the library actually sees, not just the shared Book row. Records who took the backup and when (Library.lastBackupAt/lastBackupByUserId) and shows it above the button. A separate "Download import template" link produces the same file shape with zero data rows -- literally what a real export produces for an empty library.
- Import: drag-and-drop or file-picker CSV upload, parsed and column-mapped entirely in the browser (src/lib/csv.ts's isomorphic parseCsv) before anything reaches the server. The mapping screen auto-matches columns by name, lets any column be manually remapped or ignored via a dropdown in its header, and disables a target field in every other column's dropdown once one column claims it -- so the same field can never be mapped twice, a bug caught during the mockup round rather than in production.
- Import matches rows to existing copies by Copy ID (from a prior export), not ISBN -- ISBN alone can't tell two physical copies of the same book apart. A row with no Copy ID, or one this library doesn't recognize, always creates a new copy rather than merging into an existing one; a matched row only touches the fields it actually supplies, leaving everything else on that copy untouched (real upsert semantics, not a blind overwrite). Every ISBN is validated with the same cleanIsbn/isValidIsbn rules scan-in already uses; rows with a missing or malformed ISBN are skipped and reported as separate counts on the confirm screen, which now runs a real dry-run against the database (a `dryRun` mode on POST /api/library/import that does the same Copy ID/ISBN checks with zero writes) so the new/updated/skipped counts shown before committing are exactly what the real import will do, not an estimate.
- A brand-new ISBN encountered during import never triggers a live Google Books/Open Library lookup -- that's the same external-call path that already caused a production timeout once for a single scan-in, and an import can easily contain dozens of new ISBNs. Instead it gets a bare Book placeholder marked "manual-unresolved" (reusing scan-in's own failed-lookup marker), which scan-in already retries automatically the next time that ISBN is scanned in anywhere. Any book-content fields (title/authors/publisher) a row supplies are written as this library's BookOverride, never onto the shared Book row -- so importing bad or guessed data into one library can't corrupt what another library sharing that ISBN sees, the same protection the manual book-edit form already has.
- Added a "Look up this ISBN" button to the book-edit page for any book still marked manual-unresolved, capped at one manual attempt per copy (Book.manualLookupAttempts) so it can't be spammed on a book that genuinely isn't in either catalog -- but this cap is completely separate from, and doesn't limit, scan-in's own automatic retry, since that only ever fires once per real physical scan and the catalogs it checks keep growing. A successful lookup -- whether a real catalog hit or one already resolved a moment earlier by a different copy of the same book, which skips the network call entirely -- always wins over whatever was on the page and is written straight to the database immediately, with no separate save step, so nothing is lost if the page is closed without saving. It also deletes this library's existing BookOverride for that book rather than leaving it in place: an override otherwise always wins over the canonical Book in the merged view, which would make the button look like it does nothing if a library had already saved its own correction for a still-unidentified book.
