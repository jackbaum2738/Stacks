STACKS CHANGELOG
================

Versioning: x.0.0 = major (new features) | 1.x.0 = minor (small additions/changes, batched) | 1.0.x = patch (tiny fixes/tweaks)


6.8.0 -- 2026-09-17
--------------------
- Restyled the library picker dropdown in the dashboard header: it's now a button + listbox styled like the reservation picker's suggestion menu (paper-shadow, our border and radius, chip-hover rows) instead of a plain browser `<select>`, whose open list is unstyled OS chrome no CSS can reach. The trigger keeps its previous size/position/font so it doesn't disturb the header layout. "+ New library..." moved out of the option list into its own accent-colored row below a divider, matching how the reservation picker breaks "add a new person" out from its match list, and still opens the same inline create-library form as before. Built as a `role="combobox"` button that owns focus throughout (via `aria-activedescendant` rather than moving focus into the popup) so keyboard support works the same way whether the menu was opened by mouse or keyboard: arrow keys move the highlight and wrap at the ends, Home/End jump to the first/last row (the "+ New library" row included, so it's reachable without a mouse), Enter/Space selects, Escape closes and returns focus to the trigger, and typing jumps to the next library starting with that letter. Mocked up first as an Artifact before any code was written.


6.7.0 -- 2026-09-17
--------------------
- Added a People directory: a new "People" tab listing everyone books get reserved for, replacing the old free-text "reserved for"/"contact" fields on Reservation. Promoted the reservee from a plain string into a real `Person` model scoped to a library (name, email, phone, location, birthday -- only name required), with `Reservation.personId` pointing at it. Duplicate names are allowed on purpose (two real people can share a name) -- email is the only field that has to be unique per library, and it can still be left blank, since a nullable column's NULLs never collide with each other in Postgres. A migration groups/dedupes existing `reservedFor` strings into one Person per (library, name) pair and rewires every Reservation before dropping the old columns.
- The reservation form's "Reserved for" field is now a live search-and-select against the People directory (matches as you type) instead of a plain text box, with the ability to add a brand-new person inline, right from the reservation form, for the common case of reserving for someone new. Editing an existing reservation reuses the same picker.
- People can be added, edited, and removed from the new People tab -- searchable by name or email, every column sortable ascending/descending (including active reservation count) same as the Library page. Unlike a Copy, removing a Person is always allowed even while they're currently holding books (a Person isn't a user account) -- the confirmation wording just changes to say how many books will be released back to Available, mirroring how removing a reserved copy already warns before releasing it. Member and above can add/edit/remove people, one tier lower than shelf/settings management, since a person record carries no account access of its own.
- The CSV backup/export is now a `.zip` of two files, `books.csv` and `people.csv`, instead of one flat CSV. A person-per-copy-row export can only ever list people who currently hold a book, so anyone with zero active reservations would have been silently dropped from a single combined file; `people.csv` is exported from the full People directory independently of any reservation, so nobody is lost. "Reserved For Person ID" is a new column on `books.csv` alongside the existing "Reserved For" name, since two people can now share a name and only the ID reliably picks the right one back out on re-import.
- Import now accepts that same `.zip`, or either `books.csv`/`people.csv` on its own (the uploader sniffs the filename/headers to tell them apart) -- useful for bulk-editing contact details via `people.csv` alone, or importing a legacy `books.csv` export with no people file at all. A zip imports people first, then books, so a book row can match its reservee's exact Person ID as soon as that person exists. `people.csv` alone matches rows by Person ID only, exactly like Copy ID -- no name/email fallback, so a row with no ID (or one that doesn't match) always creates a new person rather than guessing. A `books.csv` row's Person ID is checked first when present; a blank cell falls back to matching "Reserved For" by name (same as today), auto-creating a bare Person for an unrecognized name (mirroring how an unrecognized shelf name auto-creates a Shelf) -- and, since duplicate names are now possible, a name matching *more than one* existing person with no ID to disambiguate always creates a fresh Person rather than guessing which one and attaching the reservation to the wrong record. The import wizard's mapping, confirm, in-progress, and results screens all now show Books and/or People sections depending on what was actually uploaded, mocked up interactively over several rounds before building.

6.4.0 -- 2026-09-17
--------------------
- Added a real permission system: alongside Owner, a library now has Admin, Member, and View Only roles, replacing the old setup where every non-owner had the same access and "Admin" existed in the schema but nothing could ever grant it. Admin can do everything a Member can plus manage shelves, invite links, CSV import, and other members' roles. Member can scan/reserve/edit books but not touch settings. View Only is read-only -- can't scan, reserve, edit, or add notes at all. Rules worked out and agreed with the user before building: Member is deliberately excluded from CSV import (not just shelf management) because import auto-creates a Shelf row for any unrecognized shelf name in the file, which would otherwise let a Member create shelves indirectly through the back door of a feature they're supposed to be locked out of.
- The single library-wide invite link is now three separate links -- "Invite as Admin", "Invite as Member", "Invite as View Only" -- each independently generated/regenerated in Settings, since there's still no transactional email to target an invite at one person's role individually. Owner is never a link target; the only way to become Owner is a transfer. `Library.inviteCode` (unique, single column) is replaced by `inviteCodeAdmin`/`inviteCodeMember`/`inviteCodeViewOnly`; the migration copies any already-shared link into `inviteCodeAdmin` so it keeps granting the same access it always did (the old link always granted full read/write access, which is what Admin represents now).
- Added ownership transfer ("Make owner" on another member's row) -- the only way anyone, including the current Owner, stops being Owner. A Membership row with role OWNER can never be deleted or have its role changed through the regular member-management endpoints (enforced server-side, not just hidden in the UI), so an Owner who wants to leave the library transfers ownership first, then removes their own now-Admin membership like anyone else. This also means an Admin can never remove or demote the Owner, by construction rather than by a member-count check.
- Every plain "Member" from before this change is promoted to Admin in the migration -- that role already had full read/write access (everything short of managing members/invites/deleting the library, none of which the old UI even exposed), so nobody's access shrinks the moment this ships. The new, narrower "Member" tier only applies to accounts created after this point.
- Centralized the role checks in src/lib/permissions.ts and a `require: "edit" | "manage"` option on requireLibraryContext (src/lib/api-context.ts) rather than repeating role comparisons in every route, and a LibraryRoleProvider React context (src/components/library-role-context.tsx) so client components (the Scan station, the Library browse/grid view, book detail) can hide actions a View Only member can't take without each one re-deriving the role from scratch.


6.3.0 -- 2026-09-17
--------------------
- Added a Light / Dark / System theme switcher to Settings, so the app no longer has to follow the OS preference. Choice is stored per browser (localStorage), not per account -- deliberate, since it's a device-level display preference and keeping it there avoids a schema change and lets a shared device revert with no account switching. A blocking inline script in the root layout applies a stored choice before first paint, so there's no flash of the wrong theme on load.
- This needed touching how dark mode itself works, not just adding a toggle: the existing `@media (prefers-color-scheme: dark)` block in globals.css only ever reflected the OS, with no way to override it. It's now guarded so an explicit choice wins -- a `data-theme="light"|"dark"` attribute on <html> (absent for "System") -- with the same dark variable set duplicated under a new `:root[data-theme="dark"]` block for the explicit-dark case. Tailwind's own `dark:` variant (used in one place, book-cover.tsx, to swap which token a border/background uses rather than just riding a token's own light/dark value) defaults to OS-only in Tailwind v4 regardless of this, so it's now redefined via `@custom-variant dark` to also honor `data-theme`, or it would have silently ignored an explicit choice.



6.2.0 -- 2026-09-16
--------------------
- Added a real progress indicator to the import loading screen: a determinate progress bar, a "Row X of Y" counter with percentage, a ticker naming the book currently being processed, and a live New/Updated/Skipped tally that updates as it goes -- so a large import (hundreds of rows) reads as visibly working the whole way through, not just a static "Importing..." label for however long it takes. Mocked up first as an Artifact over a couple of rounds before building.
- This required changing how import actually runs, not just the UI: previously the whole file was sent as one request that only replied once every row was done, which had two problems -- no way to show real progress mid-request, and (worse) a real risk of the whole thing rolling back or dying if the connection dropped before that one giant response ever came back. Now the client splits the file into batches of 10 rows and sends them one at a time, each one committing fully before the next is sent, so closing the tab mid-import only loses whatever hasn't been sent yet -- everything already processed stays saved. If a batch request fails outright, the confirm screen reports exactly how many of the file's rows made it in before stopping, since by then some already have -- re-running the same file is safe and picks up the rest (Copy-ID-matched rows just re-match harmlessly).
- The progress bar/ticker still read as continuously moving even though the batches arrive in chunks: each batch's rows are revealed to the UI one at a time at a pace that adapts to how long that batch actually took, rather than jumping straight to the new totals the instant a batch's response lands. The import endpoint now returns a per-row outcome list (not just aggregate counts) specifically so the client has real data to animate through, rather than faking movement.

6.0.0 -- 2026-09-15
--------------------
- Added CSV backup and import to Settings, in a new "Backup & Import" block. Mocked up first as an interactive Artifact over several rounds before any code was written -- see that session's design decisions below, since most of this feature's behavior was worked out there rather than while building.
- Backup: a "Download CSV backup" button exports every non-removed copy (Copy ID, ISBN, effective title/authors/publisher, shelf, status, reservation, notes, BookCrossing ID, date added) using the library's override-merged view (applyBookOverride), so a backup reflects what the library actually sees, not just the shared Book row. Records who took the backup and when (Library.lastBackupAt/lastBackupByUserId) and shows it above the button. A separate "Download import template" link produces the same file shape with zero data rows -- literally what a real export produces for an empty library.
- Import: drag-and-drop or file-picker CSV upload, parsed and column-mapped entirely in the browser (src/lib/csv.ts's isomorphic parseCsv) before anything reaches the server. The mapping screen auto-matches columns by name, lets any column be manually remapped or ignored via a dropdown in its header, and disables a target field in every other column's dropdown once one column claims it -- so the same field can never be mapped twice, a bug caught during the mockup round rather than in production.
- Import matches rows to existing copies by Copy ID (from a prior export), not ISBN -- ISBN alone can't tell two physical copies of the same book apart. A row with no Copy ID, or one this library doesn't recognize, always creates a new copy rather than merging into an existing one; a matched row only touches the fields it actually supplies, leaving everything else on that copy untouched (real upsert semantics, not a blind overwrite). Every ISBN is validated with the same cleanIsbn/isValidIsbn rules scan-in already uses; rows with a missing or malformed ISBN are skipped and reported as separate counts on the confirm screen, which now runs a real dry-run against the database (a `dryRun` mode on POST /api/library/import that does the same Copy ID/ISBN checks with zero writes) so the new/updated/skipped counts shown before committing are exactly what the real import will do, not an estimate.
- A brand-new ISBN encountered during import never triggers a live Google Books/Open Library lookup -- that's the same external-call path that already caused a production timeout once for a single scan-in, and an import can easily contain dozens of new ISBNs. Instead it gets a bare Book placeholder marked "manual-unresolved" (reusing scan-in's own failed-lookup marker), which scan-in already retries automatically the next time that ISBN is scanned in anywhere. Any book-content fields (title/authors/publisher) a row supplies are written as this library's BookOverride, never onto the shared Book row -- so importing bad or guessed data into one library can't corrupt what another library sharing that ISBN sees, the same protection the manual book-edit form already has.
- Added a "Look up this ISBN" button to the book-edit page for any book still marked manual-unresolved, capped at one manual attempt per copy (Book.manualLookupAttempts) so it can't be spammed on a book that genuinely isn't in either catalog -- but this cap is completely separate from, and doesn't limit, scan-in's own automatic retry, since that only ever fires once per real physical scan and the catalogs it checks keep growing. A successful lookup -- whether a real catalog hit or one already resolved a moment earlier by a different copy of the same book, which skips the network call entirely -- always wins over whatever was on the page and is written straight to the database immediately, with no separate save step, so nothing is lost if the page is closed without saving. It also deletes this library's existing BookOverride for that book rather than leaving it in place: an override otherwise always wins over the canonical Book in the merged view, which would make the button look like it does nothing if a library had already saved its own correction for a still-unidentified book.

5.0.0 -- 2026-09-14
--------------------

4.0.0 -- 2026-09-14
--------------------
- The Library page now has a list/grid view toggle (remembered per browser). List view is a sortable table -- click any column header (Title, Author, Shelf, Date added, Status) to sort by it, click again to reverse. Grid view shows cover-forward cards with a checkbox that appears on hover.
- Clicking a book (a row, or a cover in grid view) now opens a full detail page with a larger cover, publisher/page-count facts, the description, and Reserve/Remove actions, instead of nothing -- there was previously no way to see a single book's full information.
- Each row/card now has its own reserve and delete icon buttons, plus checkboxes for multi-select with a bulk action bar (Reserve, Edit reservations, Delete) once anything's selected, so clearing out or reserving several books at once no longer means repeating the same action one at a time.
- Reworked "unreserve" into "edit reservation" everywhere a reservation can be changed (row icon, grid right-click menu, detail page, bulk bar): it now opens the existing reservation's details for editing (change who it's for, or remove it) instead of only offering a one-click release. Editing a bulk selection with mixed reservees prefills the name field blank rather than guessing.
- Fixed a bug where releasing a reservation only flagged it released instead of removing it, which left it permanently attached to its copy (via a one-reservation-per-copy database constraint) -- so the book's reservation banner never actually cleared, and reserving that same copy again for someone else always failed. Releasing now removes the reservation outright.


3.0.0 -- 2026-09-12
--------------------
- Added a Settings page that consolidates shelf management (rename/delete), member management (view roles, remove someone from the library), the invite link, and library deletion in one place, replacing the standalone Members page.
- Owners can now delete a library outright, from a danger-zone section that requires typing the library's exact name to confirm -- it permanently removes every shelf, book, and reservation in it for everyone with access.
- Owners/admins can remove a member from a library. The only safeguard: you can't remove a library's last remaining owner, so a library can never end up ownerless.

1.1.0 -- 2026-09-12
--------------------
- The reservation form now suggests previously-used names as you type (still lets you enter a new one), so the same person doesn't end up on the books under several slightly different spellings.

1.0.0 -- 2026-09-12
--------------------
- Initial release: scan a book in or out of a library by ISBN, using a USB/Bluetooth barcode scanner (or typing the code) on desktop, or a phone's camera on mobile. Book details are looked up automatically from Google Books, with Open Library as a fallback for anything Google Books can't resolve.
- Organize books onto shelves, browse a shelf's contents, and search the whole library by title, author, or ISBN.
- Reserve a copy for a specific person and release the reservation later; scanning a reserved copy back out automatically marks the reservation fulfilled.
- Deployed on Vercel with a Postgres database on Neon.
